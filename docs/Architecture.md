# Архитектура Memory Game

## 1. Основания и статус

Это план реализации «Галактической памяти» в стиле «Звёздных войн». Он опирается на [задание RS School](https://github.com/rolling-scopes-school/tasks/blob/master/tasks/memory-game/README.md), проверенное 5 октября 2026 года, [ТЗ](./TermsOfReference.md), [стек](./TechnologyStack.md), [дизайн](./DESIGN.md) и [правила проекта](../AGENTS.md). Функциональные требования задания имеют приоритет; имена файлов, контракты и выбранные алгоритмы ниже — решения нашего проекта.

Игра, интерфейс, восемь образов и рубашка, общая модальная оболочка и рейтинг реализованы по описанным контрактам. Локальная приёмка пройдена; результаты и ограничение проверки деплоя зафиксированы в [AcceptanceValidation](./AcceptanceValidation.md).

Стек сохраняется: HTML, CSS, vanilla JavaScript с нативными ES modules, DOM API и `localStorage`. Сервер, база данных, сборщик и внешние зависимости не нужны. Линтер не настроен; используются встроенный node:test и браузерные тестовые страницы без внешних зависимостей. Все импорты относительные, с расширением `.js`; запуск — через статический HTTP-сервер согласно [README](../README.md).

## 2. Структура модулей

Новые JS-файлы создаются при реализации своей функциональности, а не как пустые заготовки. Существующие каталоги сохраняются.

```text
memory-game/
├── index.html
├── src/
│   ├── main.js
│   ├── game/
│   │   ├── cards.js
│   │   ├── shuffle.js
│   │   ├── state.js
│   │   └── engine.js
│   ├── ui/
│   │   ├── app-view.js
│   │   ├── modal.js
│   │   └── modal-content.js
│   ├── storage/
│   │   └── leaderboard.js
│   ├── utils/
│   │   └── format-date.js
│   └── styles/style.css
├── public/assets/images/cards/
└── docs/
```

| Модуль | Ответственность |
| --- | --- |
| `main.js` | Создание экземпляров, подключение обработчиков, отображение изменений, запись победы и открытие окон |
| `game/cards.js` | Восемь описаний образов `{ pairId, label, imageUrl }` и путь общей рубашки; без DOM и загрузки данных |
| `game/shuffle.js` | Перемешивание копии массива алгоритмом Фишера — Йейтса; исходный массив не меняется |
| `game/state.js` | Создание колоды и чистые переходы состояния: выбор, совпадение, закрытие несовпадения |
| `game/engine.js` | Единственное актуальное состояние партии, таймер, перезапуск и уведомление об изменении |
| `ui/app-view.js` | Главный экран, ссылки на карточки и счётчики, обработчики действий, отображение снимка |
| `ui/modal.js` | Одна переиспользуемая оболочка: открытие, закрытие, фон, прокрутка и фокус |
| `ui/modal-content.js` | Создание DOM-содержимого победы и рейтинга; без самостоятельных модальных оболочек |
| `storage/leaderboard.js` | Чтение, проверка, сортировка, ограничение топ-10 и запись; резервное хранение в памяти |
| `utils/format-date.js` | Форматирование времени завершения в `ДД.ММ.ГГГГ` в часовом поясе браузера |
| `styles/style.css` | Токены DESIGN, сетка 4 × 4, состояния карточек, окна, адаптивность и reduced motion |

Восемь образов выбираются из DESIGN, реальные файлы добавляются позднее. `public` — обычный каталог: URLs ресурсов начинаются с `./public/assets/images/cards/`, а не с `/assets/`. Данные в JS позволяют начать игру без отдельного `fetch` и его состояния загрузки.

## 3. Направление зависимостей

```text
index.html → main.js
main.js → cards.js, engine.js, app-view.js, modal.js,
          modal-content.js, leaderboard.js
engine.js → state.js
state.js → shuffle.js
modal-content.js → format-date.js
```

`main.js` передаёт описания карточек в engine и view. UI получает действия как callbacks, engine передаёт изменения через callback. Ни game, ни storage не импортируют UI или `main.js`; UI не импортирует engine или storage. Замыкания заменяют глобальные переменные. Общий event bus, классы, DI-контейнер и самописный фреймворк здесь не нужны.

## 4. Состояние и переходы игры

Состояние хранит engine; DOM — его отображение. UI не выводит игровую логику из CSS-классов. Внутренняя структура:

```js
{
  roundId: 1,
  deck: [{ id: '1:lightsaber:0', pairId: 'lightsaber', status: 'closed' }],
  phase: 'idle',
  firstCardId: null,
  secondCardId: null,
  moves: 0,
  matchedPairs: 0,
  completedAt: null
}
```

Пример показывает одну запись; настоящая колода содержит 16. `id` уникален для экземпляра карточки в партии, `pairId` одинаков для двух экземпляров образа. Статусы: `closed`, `open`, `matched`. Метаданные изображения находятся в каталоге образов, а не используются для сравнения пар.

| Фаза | Выбор и переход |
| --- | --- |
| `idle` | Закрытая карточка → `open`, устанавливается `firstCardId`, фаза `one-open` |
| `one-open` | Вторая другая закрытая карточка открывается, `moves` увеличивается ровно на 1 |
| Совпадение второй карточки | Обе получают `matched`, `matchedPairs` увеличивается; выбор очищается, фаза `idle` либо `finished` |
| `waiting-mismatch` | Две несовпавшие карточки открыты, выбор блокируется; после 1000 мс обе закрываются, выбор очищается, фаза `idle` |
| `finished` | Все восемь пар найдены, карточки больше не выбираются; работает только перезапуск и просмотр рейтинга |

Сначала engine проверяет фазу, наличие карточки и `status === 'closed'`. Неизвестный ID, повторный клик, найденная пара и клик во время ожидания/после завершения ничего не меняют и не уведомляют UI.

Инварианты:

- В каждой колоде 16 уникальных ID и восемь `pairId`, каждый встречается дважды.
- `moves` увеличивается только при второй допустимой карточке; первая не запускает таймер.
- В `idle`/`finished` нет выбранных ID; в `one-open` есть только первый; в `waiting-mismatch` — два разных.
- Одновременно открыты не более двух ненайденных карточек; найденные не закрываются.
- `matchedPairs` равен половине числа карточек `matched`; значение от 0 до 8.
- `completedAt` задаётся один раз при переходе в `finished`; до этого равно `null`.

## 5. Контракты game и таймер

Это предлагаемые сигнатуры обычных JS-функций, без дополнительной системы типов.

| Функция | Контракт |
| --- | --- |
| `shuffle(items, random = Math.random)` | Возвращает перемешанную копию массива |
| `createInitialState({ pairIds, roundId, random })` | Создаёт 16 закрытых карточек и нулевые счётчики |
| `selectCard(state, cardId, completedAt)` | Чистая функция: возвращает `{ state, kind }`; kind: `ignored`, `first-opened`, `matched`, `mismatch`, `finished`; вход не меняется |
| `resolveMismatch(state)` | Чистая функция: закрывает выбранную пару только в `waiting-mismatch`; иначе возвращает исходное состояние |
| `createGame({ pairIds, onChange, random = Math.random, now = Date.now, delayMs = 1000 })` | Возвращает `{ restart, choose, getSnapshot, destroy }`; сам не запускает партию и не вызывает callback при создании |
| `restart()` | Отменяет таймер, увеличивает `roundId`, создаёт состояние, синхронно вызывает `onChange(snapshot, 'started')` |
| `choose(cardId)` | Применяет `selectCard` с `now()`; при изменении уведомляет `onChange(snapshot, kind)`; при mismatch ставит один таймер |
| `getSnapshot()` | Возвращает новую копию состояния, массива и объектов карточек; изменение снимка не меняет engine |
| `destroy()` | Отменяет таймер, инвалидирует отложенные callbacks; дальнейшие действия и уведомления игнорируются |

`selectCard` использует переданный timestamp только при победе. Чистые функции не обращаются к DOM, времени, storage или таймерам. Реальные побочные действия времени принадлежат `engine.js`, что соответствует ответственности `game/` в AGENTS и ТЗ.

При несовпадении engine сразу фиксирует блокирующую фазу и ставит `setTimeout` на 1000 мс после второго выбора. Callback запоминает `roundId`; перед применением проверяет тот же раунд и фазу `waiting-mismatch`, очищает свой ID таймера, вызывает `resolveMismatch` и `onChange(snapshot, 'mismatch-resolved')`. При restart сначала выполняются `clearTimeout` и смена раунда. Даже устаревший callback не меняет новую партию.

Таймер не принадлежит модалке и не зависит от CSS-анимации. Открытие рейтинга не отменяет и не пересоздаёт его. Engine уведомляет view даже под открытым окном; обновление поля сохраняет модальное содержимое и фокус. В фоне браузер может задерживать таймер, поэтому миллисекундный интервал проверяется в активной вкладке.

## 6. Контракты UI и общая модалка

| Функция | Контракт |
| --- | --- |
| `createAppView({ cards, backImageUrl, onCard, onNewGame, onLeaderboard })` | Создаёт и добавляет главный экран; возвращает `{ root, render, getNewGameButton, destroy }` |
| `view.render(snapshot)` | Обновляет поле и счётчики; пересоздаёт карточки только при смене раунда, не касается модалки |
| `createModal({ backgroundRoot })` | Создаёт одну оболочку рядом с главным экраном; возвращает `{ open, close, isOpen, destroy }` |
| `modal.open({ title, content, returnFocus })` | Принимает DOM-узел, задаёт заголовок, блокирует фон/скролл и переводит фокус внутрь; при повторном открытии заменяет содержимое той же оболочки |
| `modal.close()` | Идемпотентно закрывает окно и восстанавливает прежние стили прокрутки, доступность фона и фокус |
| `createVictoryContent({ moves, persistence, onNewGame, onClose })` | Возвращает DOM-узел с итогом и действиями |
| `createLeaderboardContent({ results, persistence, onClose })` | Возвращает DOM-узел с таблицей либо пустым состоянием и сообщением о недоступном сохранении |

Выбираем собственную оболочку: overlay и панель `role="dialog"`, `aria-modal="true"`, заголовок с `aria-labelledby`. При открытии `backgroundRoot.inert = true`, прежний inline `overflow` сохраняется и заменяется блокировкой прокрутки. Tab/Shift+Tab удерживаются среди доступных элементов окна. Escape и кнопка вызывают общий `close`; фон закрывает только при `event.target === overlay`. События содержимого не закрывают окно.

При закрытии восстанавливаются исходные значения `inert` и `overflow`. Фокус возвращается в переданный подключённый доступный элемент; резерв — кнопка «Новая игра» хедера. Для автоматической победы сразу передаётся эта кнопка. Обработчики оболочки подключаются один раз; `destroy` закрывает окно и удаляет обработчики.

Карточки — настоящие `button`. View блокирует их при недопустимом статусе/фазе; engine всё равно проверяет выбор самостоятельно. Кнопки хедера не блокируются фазой несовпадения. Закрытая карточка имеет имя «Карточка N, закрыта», лицевая сторона скрыта визуально и из доступности. После открытия имя отражает образ, а изображение не дублирует подпись. Ошибка загрузки заменяется текстом образа только на открытой стороне. Счётчики и итог пары объявляются кратко через `aria-live="polite"`.

Все элементы создаются `document.createElement`, текст — `textContent`, дерево — `append`, `replaceChildren`, `remove`. Исходный `<body>` содержит только `<script>`. Запрещены запись в `innerHTML`/`outerHTML` даже пустой строки, `insertAdjacentHTML`, `document.write`/`writeln`, разбор HTML через `DOMParser`/`Range.createContextualFragment`, `alert`/`confirm`/`prompt` и сторонние библиотеки UI/DOM/игровой логики.

## 7. Контракт рейтинга и устойчивость

`createLeaderboardStore()` возвращает `{ getResults, addResult }`. Доступ к `window.localStorage`, чтение, `JSON.parse` и запись защищаются обработкой ошибок. Ключ проекта: `memory-game.leaderboard.v1`; значение — JSON-массив `{ moves, completedAt }` согласно ТЗ. Другие ключи не читаются и не меняются.

- `getResults()` возвращает `{ results, persistence }`: копию нормализованного топ-10 и режим `persistent` либо `memory`. Первый вызов загружает данные; следующие используют единый список текущего сеанса.
- `addResult({ moves, completedAt })` проверяет запись, добавляет в тот же список, сортирует, обрезает до 10, пытается сохранить и возвращает `{ results, persistence }`. Некорректный аргумент отклоняется без изменения списка.
- `moves` — безопасное целое не меньше 8; `completedAt` — безопасное целое не меньше 0, для которого `Date` допустима. При чтении не-массив/повреждённый JSON дают пустой список, некорректные элементы игнорируются.
- Сортировка: `moves` по возрастанию, затем `completedAt` по возрастанию; при полном равенстве сохраняется порядок добавления. Одинаковые результаты разных партий допустимы.
- Место вычисляется как индекс + 1; в storage не сохраняются место, форматированная дата и состояние незавершённой игры.
- При ошибке доступа/записи store переходит в `memory` до конца сеанса, сохраняя пригодные прочитанные и новые результаты. Последующий просмотр не заменяет их старым содержимым storage. Игра работает, UI сообщает об отсутствии постоянного сохранения; после перезагрузки такие результаты могут потеряться.

За однократность отвечает `main.js`: хранит `handledRoundId`, при событии `finished` сначала отмечает раунд обработанным, затем вызывает `addResult` и открывает победу. Дата берётся из `snapshot.completedAt`, не вычисляется повторно при показе окон. Закрытие победы, просмотр рейтинга и перезапуск не вызывают `addResult`. Неудачная запись также не вызывает повторного добавления: результат уже есть в памяти.

## 8. Потоки приложения

1. **Загрузка:** main создаёт store, engine, view и modal; callbacks обращаются к готовым экземплярам. Загружает рейтинг, затем вызывает `game.restart()`. Callback `started` отображает поле. Начальной кнопки запуска нет.
2. **Выбор:** view передаёт ID в main; main проверяет, что модалка закрыта, вызывает `game.choose`. Engine изменяет состояние и уведомляет view; первый выбор не увеличивает ходы, второй увеличивает.
3. **Совпадение/несовпадение:** совпавшие остаются видимыми; несовпадение блокирует выбор, а через 1000 мс engine обновляет поле и разблокирует карточки.
4. **Победа:** main отображает завершённый снимок, однократно записывает результат и открывает общую модалку с содержимым победы. Завершённое поле остаётся видимым после закрытия.
5. **Рейтинг:** main получает список store и открывает ту же оболочку. Engine не меняется; текущий таймер продолжает работать. Закрытие не вызывает restart или запись результата.
6. **Новая игра:** обе кнопки используют один handler main: `modal.close()`, затем `game.restart()`. Отмена таймера и смена состояния происходят сразу; рейтинг сохраняется.

Только main решает, какое окно открыть и когда записать победу. `onChange` синхронен и не запускает повторный выбор/перезапуск из обработчика отображения. При необходимости завершения жизненного цикла main вызывает `game.destroy()`, `modal.destroy()` и `view.destroy()`; эти методы освобождают свои ресурсы.

## 9. Проверка реализации

Порядок: данные и изображения → чистые переходы и engine → главный экран и CSS → общая модалка → store и соединение в main → проверки и обновление README. Каждый модуль появляется с работающей ответственностью.

После реализации проверить сценарии приёмки из ТЗ, особенно:

- Переходы состояния: повторный ID, третья карточка, найденная пара, правильные счётчики, восемь пар и неизменяемость снимков.
- Таймер: одно несовпадение — один таймер; немедленный restart; старый callback не меняет первый выбор новой партии; рейтинг не ставит ожидание на паузу.
- Рейтинг: сортировка равных ходов/времён, 11 записей → топ-10, одна запись за раунд, повреждённый JSON и отказ storage с сохранением списка сеанса.
- Браузер: три способа закрытия обоих окон, фон/скролл/фокус, клавиатура, скрытые имена, картинки, ширины 320/375/768/1440 px и reduced motion.
- Исходники: только script в body, отсутствие запрещённых операций, корректные относительные пути локально и на деплое, отсутствие ошибок консоли.

Чистые переходы, нормализация рейтинга и таймер проверяются через node:test; тесты движка используют управляемые таймеры. DOM, фокус и адаптивность проверяются в браузере. Установка инструментов, Git-операции и публикация требуют отдельного указания пользователя. Фактические результаты локальной приёмки приведены в [AcceptanceValidation](./AcceptanceValidation.md); проверка опубликованного адреса ожидает этап деплоя.
